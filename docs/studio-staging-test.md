# First Studio staging test

The setup scripts generate local artifacts. Cloud provisioning and the live test each require owner approval. Use synthetic staging data and leave the production Studio database and Workers alone.

1. **Pin and smoke-test the image.** After this setup PR is merged, fetch `origin/main`, review its full SHA and check out that commit. Run `sh sites/studio/executor/smoke-image.sh "$BASE_SHA"` with Docker running. Save the printed image ID and SHA. The test builds Linux amd64, checks 403 without a token, 400 for markup and 200 with passing repository checks and a digest. Push that same image ID to Artifact Registry after provisioning is approved. Record the registry digest after the push. If main changes before the trial, repeat from the new reviewed main. Local Docker may pull public base images and npm dependencies.
2. **Cloudflare staging D1 and Access.** In the existing account, open **Storage & databases → D1 SQL database → Create database** and name it `zane-studio-staging`. Record both staging and production database UUIDs and compare them. In **Zero Trust → Access controls → Applications → Add an application → Self-hosted**, configure all paths on `studio-staging.zanegiordano.com` for the owner email only. Copy the application audience and team origin. Attach the hostname only after the Access policy is in place. [Cloudflare Access setup](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)
3. **Generate and apply the staging plan.** Run the generator below with a new output directory outside the repo. Inspect both Worker names and D1 UUIDs. Using staging-only release credentials, run the two D1 commands below, check the returned marker equals the staging UUID, then deploy the two configs separately with Wrangler. Store `ACCESS_TEAM_ORIGIN`, `ACCESS_AUD`, and `STUDIO_OWNER_EMAIL` on the web Worker. In **Workers & Pages → zane-studio-staging → Settings → Domains & Routes → Add → Custom Domain**, attach the staging hostname. Verify an anonymous request is redirected to Access and the owner can open Activity. The dispatcher has no route, schedule, task ID, or active model configuration.
4. **Google Cloud validator.** In a dedicated staging project open **APIs & Services → Library** and enable Cloud Run, Artifact Registry and Secret Manager. In **Artifact Registry → Repositories → Create repository**, create Docker repository `studio-staging` in the chosen region. In **IAM & Admin → Service Accounts → Create service account**, create `studio-validator-staging` with no project role. In **Security → Secret Manager → Create secret**, create `studio-validator-staging` with a random token of at least 32 bytes. On that secret’s **Permissions → Grant access**, grant the runtime service account Secret Manager Secret Accessor on this secret only. Push the smoke-tested image, then run `sh sites/studio/executor/cloud-run-plan.sh "$PROJECT" "$REGION" "$IMAGE_DIGEST_URI" "$SECRET_VERSION"` to print the proposed deploy command. Review and run it after approval. Check Cloud Run’s active revision uses that digest, the dedicated account, zero minimum instances, maximum one instance and concurrency one. Repeat the unauthenticated and authenticated smoke probes against its HTTPS URL using the real checker secret from secure storage. Cloud Run requests, Artifact Registry storage and Google Cloud egress can incur charges. [Cloud Run deploy reference](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy)
5. **Owner credentials.** In OpenAI Platform open **Settings → Organization → Projects → Create project**, then the staging project’s **API Keys → Create new secret key → Restricted**. Allow Responses write, confirm standard pricing and access to `gpt-4.1-mini-2025-04-14`, and store the key as dispatcher secret `STUDIO_OPENAI_KEY`. In GitHub open **Settings → Developer settings → GitHub Apps → New GitHub App**. Disable webhooks, grant Contents and Pull requests read/write, generate a private key, and use **Install App → Only select repositories → enaz333/zane-websites**. Keep the App off branch-protection bypass lists. Store the PEM as `STUDIO_GITHUB_PRIVATE_KEY` and the checker token as `STUDIO_CHECK_SECRET` on the dispatcher only. Use **Workers & Pages → zane-studio-dispatch-staging → Settings → Variables and Secrets** or Wrangler secret input. OpenAI inference can incur charges. Cloudflare Workers and D1 usage may count toward paid usage. [OpenAI project settings](https://platform.openai.com/settings/organization/projects) · [GitHub App settings](https://github.com/settings/apps)
6. **Approve one live task.** With the dispatcher disabled, submit one ASAP Edit from the phone for Personal site `/`, asking to change “A little of everything.” to “Selected projects.” Read the UUID from staging’s owner-authenticated `/api/tasks` response. Review the validator digest, staging D1 UUID, task UUID, and budget together. In the dispatcher config set `STUDIO_TEST_TASK_ID`, `STUDIO_CHECK_ORIGIN`, numeric `STUDIO_GITHUB_APP_ID` and `STUDIO_GITHUB_INSTALLATION_ID`, and `STUDIO_RATE_CARD=gpt-4.1-mini-2025-04-14:standard:0.40:1.60`. Keep both budget values at `419440`. Only after explicit approval set `STUDIO_EXECUTION_ENABLED` to `true` and add `"triggers": {"crons": ["*/2 * * * *"]}` to the staging dispatcher. Redeploy that config and take both Macs offline. The dispatcher itself requires a successful synthetic check against the running validator before calling OpenAI. A failed preflight consumes the conservative ledger reservation and requires review before any retry.
7. **Verify and stop.** From the phone confirm Activity reaches PR ready with passing checks and links to one open draft. Inspect its single heading change and the reviewed SHA as its commit parent. Disable the staging dispatcher and remove its schedule after reconciliation. Retain the ledger and leave the draft unmerged.

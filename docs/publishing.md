# Onboarding and publishing Workers

## Add a project

1. From the repository root, run `python3 scripts/projects.py new my-project`. The template creates `sites/my-project/wrangler.json`, an isolated `public/` directory and a disabled entry in `projects.json`. The Worker will be named `zane-my-project`, with `my-project.zanegiordano.com` proposed as its hostname.
2. Add the project source. Keep public files in `public/` and any project-specific Worker code in `src/`. For a shared Worker entry point or import, list its repository-relative path in the entry's `watch` array. List service binding targets in `depends_on`. The registry validates config coverage, names, hostname uniqueness, assets boundaries, and the dependency graph. Set `subdomain` to `null` for a private binding target or a separately managed hostname.
3. Run the checks in the [README](../README.md) and preview locally with `npx wrangler dev -c sites/my-project/wrangler.json`. Open a PR with the slug, intended hostname, dependencies and local evidence. Leave `enabled` false for review-only merges. To publish, change it to true in an owner-reviewed PR. An activation PR can be combined with the source PR if the owner is ready to publish.
4. Merge the approved PR into protected `main`. Once publishing is enabled for the repository, the workflow selects Workers with changes under their site directory, changes to their registry entry, or changes to their watched shared files. A Photo Notes-only change deploys Photo Notes alone. If both Photo Notes and personal are selected, Photo Notes goes first. Unselected dependencies must already exist, and the workflow reports a failure if they cannot be verified. The first launch can use the manual workflow with `all` to establish the full graph.

## Configure GitHub before enabling publication

- Protect `main` with required pull requests, the **Validate Workers** check from GitHub Actions, and branches up to date. For a solo owner, set required PR approvals to zero and leave Code Owner review optional. Block bypass, force pushes and deletion. The owner reviews the PR and merges after CI. [GitHub branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- Create the `cloudflare-production` environment. Under **Selected branches and tags**, allow the `main` branch only. Add the owner as a required reviewer, leave **Prevent self-review** unchecked, and disable administrator bypass. Approve the queued deployment in Actions after checking its commit SHA. The workflow then publishes the approved revision automatically. [GitHub deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
- In that environment, set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_ZONE_ID` as variables. The zone ID must be for the active Cloudflare zone `zanegiordano.com`. Reserve the repository's `zane-<slug>` Worker names in the target account before enabling publication.
- Add the environment secret `CLOUDFLARE_API_TOKEN` with Workers Scripts Write/Edit scoped to the target account. Add the separate `CLOUDFLARE_DOMAIN_API_TOKEN` with Workers access to that account and Workers Routes Write plus DNS Read scoped to the `zanegiordano.com` zone. Use the narrowest available scopes and rotate tokens in GitHub. Wrangler receives the deploy token only. [Cloudflare Workers permissions](https://developers.cloudflare.com/workers/authorization/workers/)
- After staging and explicit owner approval, change the literal `false` to `true` in the publish job condition through a reviewed PR. Then set the **repository** variable `WORKERS_PUBLISH_ENABLED` to `true`. Both automatic and manual deployments require protected main and this opt-in. This variable is intentionally outside the repository. The initial five projects have no registry-managed hostnames. Their Netlify-to-Cloudflare cutover is a separate owner-controlled operation.

## Hostname protection and recovery

The deploy script asks Cloudflare to attach a Workers Custom Domain only for a registry entry with a subdomain. Cloudflare handles DNS and certificates. Before upload and again before attachment, it checks the Cloudflare Custom Domain and DNS APIs. An existing matching attachment is reused. Another Worker, a disabled attachment, or any existing exact or zone-wildcard DNS record blocks provisioning. The attachment uses the Cloudflare API endpoint used by the pinned Wrangler version, with its scope replacement and both overwrite flags explicitly disabled. Keep this behavior covered when upgrading Wrangler. Production API behavior still needs a first staging validation using an unused hostname. [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)

Publishing is serialized. Each automatic run selects projects from its push range and checks out the triggering commit SHA. Review queued runs in merge order. For recovery, dispatch a new run from current main so an older revision cannot be restored by rerunning an old job. Check the workflow log for selected Workers. If a batch fails partway, earlier Workers may already be live. Correct the failure, then run **Publish Workers** from `main` with the affected slug, or use `all` for an intentional full rollout. A disabled or removed registry entry stops selection and requires separate owner action to retire any live Worker or hostname. Changing a subdomain attaches the new hostname and leaves the old one for explicit review.

## Local verification

The registry validated all five existing projects. The Python tests covered scaffolding, disabled entries, dependency ordering, commit-range selection, and simulated Cloudflare conflicts and attachment. Wrangler dry runs passed for all five projects and a freshly scaffolded project. The two workflows were statically checked with actionlint 1.7.12, suppressing only its known false positive for GitHub’s documented [concurrency queue setting](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency). GitHub execution and live Cloudflare attachment remain unverified.

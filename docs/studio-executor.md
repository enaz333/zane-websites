# Studio executor: setup after owner approval

For the first trial, follow the [repeatable staging setup and smoke test](studio-staging-test.md).

PR B enables a single copy slot: the Personal homepage projects heading. Studio still saves all other requests for review. The executor cannot add files, edit markup, modify workflows, follow URLs from prompts, or run generated commands. The only model artifact is a plain-text replacement for the existing heading. The publisher independently rebuilds that patch from the pinned source. This is a bounded fallback, not a general Codex sandbox.

The [Agents API session schema](https://developers.openai.com/api/reference/resources/beta/subresources/agents/subresources/sessions/methods/create) does not document a caller-configurable spend ceiling covering both agent model calls and hosted sandbox charges. Its [session budget error](https://developers.openai.com/api/docs/guides/agents-api/errors) does not establish such a ceiling. This slice uses a single tool-free [Responses request](https://developers.openai.com/api/reference/resources/responses/methods/create), plus an isolated Cloud Run validator. No Agents API or OpenAI sandbox entitlement is needed for the fallback. OpenAI project access has not been tested.

## Configure staging first

1. In OpenAI Platform create a dedicated billing project. Confirm access to `gpt-6-luna`; restrict the project to that model where available. Create a restricted project key with Responses write only and store it as dispatcher secret `STUDIO_OPENAI_KEY`. Keep it out of Studio web, the validator and GitHub. Check the [published model limits and rates](https://developers.openai.com/api/docs/models/gpt-6-luna) and confirm standard, non-regional billing with no pricing uplift. Recheck rates before activation and disable dispatch if they change. Platform project alerts are supplemental.
2. Create a private [GitHub App](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app) with webhooks disabled and repository Contents and Pull requests read/write, plus the default Metadata read. Install on **only** `enaz333/zane-websites`. No Workflows, Actions, deployment or administration access; no bypass of main protection. Record the numeric App ID and installation ID. Store the generated PEM as the dispatcher secret `STUDIO_GITHUB_PRIVATE_KEY`, never in the validator. The publisher requests an installation token limited to this repository and those permissions. The dispatcher is trusted code and hosts the publisher module; the model and validator cannot invoke that module.
3. From a reviewed checkout, fetch main and select its full commit SHA. Run `context=$(sh sites/studio/executor/prepare-image.sh "$BASE_SHA")`. Build the provided Dockerfile from that context with `--build-arg STUDIO_CHECK_BASE="$BASE_SHA"`, using a Linux image supported by Cloud Run. The context contains a Git archive of that exact revision and two reviewed runner files; `npm ci` runs during build. Push the image to a private Artifact Registry and [deploy the image by digest](https://docs.cloud.google.com/run/docs/deploying) with port 8080, request timeout 310 seconds, one request per instance, max one instance, min zero, and no traffic to old revisions. Use a dedicated runtime service account with no project grants. Give it read access only to a Secret Manager secret containing a random bearer token of at least 32 bytes; map that secret to `STUDIO_CHECK_SECRET`. Grant the same token to the dispatcher. The `run.app` URL accepts requests from the Internet and rejected traffic can still incur costs or consume capacity. Monitor request volume and charges during the trial. The model ledger does not cover this traffic. The validator process rejects unauthorized requests before reading their body. Do not expose it until the secret is configured. Apply restricted outbound networking if available; dependency installation happens at build time. The checker invokes only fixed repository commands with a clean child environment, and accepts only text for the one slot. Never build from a task branch.
4. Use a **separate Studio staging D1** and an owner-only Cloudflare Access app. Apply migrations 0001–0003 to that staging database. Compare the staging D1 UUID with the production UUID in the dashboard. Using the staging database's SQL console, set its marker with `INSERT INTO studio_dispatch_environment (id, staging_id) VALUES (1, '<staging D1 UUID>');`. Set `STUDIO_STAGING_ID` on the dispatcher to the same UUID. An absent or mismatched marker prevents claims and recovery. Leave the production database unmarked. Configure the staging Studio web Worker with its own D1 and the usual four Access runtime secrets from the [private release guide](studio-release.md). Keep Workers.dev, previews and routing off until the staging Access hostname is protected. Add `STUDIO_QUEUE_ENABLED=true` to the **web Worker only** once testing the queue. Leave the approved production release workflow and existing hostname alone.
5. Copy `sites/studio/executor/wrangler.json` to an ignored file such as `sites/studio/executor/config.staging.json` (add it to your local Git exclude first), name the Worker `zane-studio-dispatch-staging`, and keep both public URL flags false. Add the staging D1 binding named `DB` with `migrations_dir: "../migrations"`. Set non-secret `vars` below and add `triggers: { "crons": ["*/2 * * * *"] }` after testing the disabled Worker. Put both API credentials and the checker token into Worker secrets through Wrangler secret input or the dashboard. Never place them in config, CLI arguments, snapshots or logs.

| Dispatcher variable | Value |
| --- | --- |
| `STUDIO_STAGING_ID` | UUID recorded in the staging D1 marker |
| `STUDIO_TEST_TASK_ID` | The UUID of the one approved staged request, obtained from staging Activity’s `GET /api/tasks` response |
| `STUDIO_BASE_SHA` | Full reviewed main SHA used to build the validator |
| `STUDIO_CHECK_ORIGIN` | Validator's exact HTTPS `run.app` origin, without a path |
| `STUDIO_GITHUB_APP_ID`, `STUDIO_GITHUB_INSTALLATION_ID` | Numeric IDs |
| `STUDIO_RATE_CARD` | `gpt-6-luna:standard:0.10:0.01:0.125:0.50:0.20:0.02:0.25:0.75` after verifying rates. Each group lists input, cached input, cache write, and output in USD per million tokens (short context first). |
| `STUDIO_RUN_MICROS`, `STUDIO_MONTH_MICROS` | Optional USD millionths; defaults 2000000 and 20000000, can only be lowered |
| `STUDIO_EXECUTION_ENABLED` | Set to `true` only for the approved test |

The dispatcher never uses inbound callbacks. Cron reclaims an expired lock, retries safe operations and reconciles GitHub from a deterministic branch and verified diff. A model request with an unknown outcome is never replayed. If GitHub remains unavailable after the deadline, the task remains reserved and reconciling until GitHub can report whether the PR exists. Keep the approved task ID and database marker set until reconciliation completes. GitHub publishes only while main matches the checked revision. If main advances, review and rebuild from the new SHA for a separately approved run. Cancellation is available until claim. ASAP controls ordering; economy waits at least 15 minutes. Neither is a delivery promise. A queued task blocked by the monthly ledger remains queued and can be cancelled.

## Budget and testing

Each claimed task reserves $0.262548 against the UTC month before any model call. This reserves 1,050,000 input tokens at the highest Standard input rate (long-context cache writes, $0.25 per million) and 64 output tokens at the long-context rate ($0.75 per million). The actual text payload is capped at 64,000 UTF-8 bytes. The request uses the global Responses endpoint, Standard processing, reasoning effort `none`, no tools, strict JSON output, and disabled truncation. The output cap includes any reasoning tokens; unexpected reasoning, wrong model or tier, incomplete results, and usage beyond the reviewed limits fail closed. The transaction also admits at most one active execution. Reservations are retained even on failure or uncertain billing, so no speculative refund permits another call. Reported token counts are retained when available; they are not billed dollar amounts. New calls stop around month rollover. The caps bound Studio's modeled AI usage under the reviewed rate card; they are not provider-enforced or total infrastructure limits. Cloud Run, build/registry, Workers and D1 may bill separately. Never reuse the project's key for other workloads.

Run the [README checks](../README.md) and the dispatcher bundle dry run: `npx --no-install wrangler deploy --dry-run -c sites/studio/executor/wrangler.json`. The Node integration test uses D1 and fixture OpenAI, validator and GitHub responses; it simulates a lost reply after draft creation. For a container smoke test run the built image locally with a synthetic `STUDIO_CHECK_SECRET`. POST to `/check` with that bearer token and JSON `{"base":"<BASE_SHA>","replacement":"Selected projects"}`. Expect `passed: true` and a SHA-256 digest. Missing credentials must return 403; a wrong base or markup must return 400.

After merging a model change, rebuild and smoke-test the validator from the new reviewed main so its base SHA matches the dispatcher. Confirm the new revision separately before enabling dispatch. For the first approved live test set both budget variables to `262548` to admit a single task in that UTC month. Start with an empty staging queue, queue intake enabled, and dispatch disabled. From the phone open protected Studio staging, choose Edit → Personal site → `/`, check ASAP and enter “Change the projects heading from ‘A little of everything.’ to ‘Selected projects’.” Read the submitted task UUID from the owner-authenticated staging `/api/tasks` response. Configure that exact ID and the two budget values on the route-free staging dispatcher. After separate approval, enable the dispatcher with its cron trigger. Shut down both Macs before the first scheduled execution and refresh Activity from the phone until the draft link appears. Verify GitHub shows the pinned SHA as the sole commit parent, only the intended heading changed, and the draft is open with checks passed in Activity. Do not merge or deploy it. Disable dispatch after the test. Before restoring or cloning D1, stop every dispatcher attached to that database. Keep the original ledger and never activate a restored or copied database with its old staging marker. Reconcile the original in-flight run first. Only repeat on the production Studio hostname after separately approving its release, D1 binding, and activation.

For rollback disable web queue intake and dispatcher scheduling/activation; retain migration 0003 and its ledger. Restore the prior web Worker using the protected Studio procedure if needed. Never manually requeue a task with an unknown model or publish outcome. Reconcile the deterministic branch and PR before any intervention.

## Dispatch and recovery diagnostics

Prepare logs `studio_dispatch_prepare` with a fixed source or validator code. Request errors, timeouts, unexpected HTTP statuses and invalid responses are retried under the same reservation. A completed preflight with failed checks ends the task. The execution deadline and attempt limit bound prepare retries. If a claim reply is unclear, the next tick uses the persisted lock and cannot create a second reservation.

An expired `model_sent` lock leaves billing uncertain. The dispatcher records `model_outcome_unknown`, closes the run and retains its reservation. Publication errors log `publication_unconfirmed`. The next tick checks the deterministic branch and draft against the pinned parent, changed path and expected bytes. After the window it only reconciles. An unavailable GitHub read leaves the task active for another reconciliation attempt. A closed, non-draft or mismatched PR requires owner inspection.

The historical one-time abort has a fixed task and reviewed preconditions. If its import reply is unclear, the script verifies the terminal row, cleared lock, preserved ledger and appended audit event using reads. `recovery_import_verified_after_unclear_response` confirms that state. `recovery_original_state_observed` describes the latest read. `recovery_verification_unavailable` and `recovery_state_mismatch` require read-only investigation. `recovery_postflight_unverified` means the D1 terminal state is already verified and only the GitHub or disabled-dispatcher postflight remains unresolved. Preserve the original evidence and inspect the task and publication state before considering any separately approved intervention.

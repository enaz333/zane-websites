# Private Studio release checklist

This procedure uses the Cloudflare account that already hosts the five public Workers. Studio has its own manual GitHub workflow and protected environment. The Studio registry entry stays disabled, and `zanegiordano.com/admin` stays inactive. Neither merging the implementation PR nor configuring GitHub starts a release.

## 1. After owner approval: prepare Cloudflare

1. Sign in to the [Cloudflare dashboard](https://dash.cloudflare.com/) and select the existing account that owns the `zanegiordano.com` zone. Open **Workers & Pages** and copy the account ID from **Account details**. Check that **zane-studio** does not already exist for a first release. Do not create it from a starter template or connect it to Workers Builds.
2. In **Storage & databases → D1 SQL database**, select **Create database**, name it exactly `zane-studio`, and create it. Open the new database and copy its **Database ID** (UUID). Leave it empty: GitHub applies [the existing migration](../sites/studio/migrations/0001_tasks.sql) with Wrangler. Keep its contents and backups private. See [Cloudflare D1 setup](https://developers.cloudflare.com/d1/get-started/).
3. Open **Zero Trust → Access controls → Applications → Add an application → Self-hosted**. Name it **Zane Studio**, choose a short session (for example, **1 hour**), then **Add public hostname**. Set **Subdomain** to `studio`, **Domain** to `zanegiordano.com` and leave **Path** empty so the app covers every path. Saving this Access app configures its policy; skip any DNS, tunnel, or routing step. See [Cloudflare self-hosted applications](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).
4. Add a policy named **Studio owner**, set **Action** to **Allow**, and add exactly one **Include → Emails** value: the exact email your identity provider returns for your account. Select only the intended identity provider under **Login methods**; prefer an account protected by MFA. Remove any other Allow, Bypass, or Service Auth rules for Studio. Check for wildcard apps and more specific path policies that could override Studio's policy; do not change other apps as part of this rollout.
5. Save the app. Open **Applications → Zane Studio → Edit → Additional settings** and copy the **Application Audience (AUD) Tag**. In Zero Trust, use the team's `https://<team>.cloudflareaccess.com` origin with no trailing slash. The runtime checks both the signed app token and the exact email. See [Access JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).
6. In the existing Cloudflare account, open **Manage Account → Account API Tokens → Create Token → Create Custom Token**. Name it **GitHub Studio release**. Add **Account → Workers Scripts → Edit** and **Account → D1 → Edit**, scoped to this account only. Cloudflare may label the equivalent API permissions **Write**. Grant no Zone/DNS, Workers Routes or Access write permissions. Pick an expiry and save the token directly to the dedicated GitHub environment in the next step. Do not reuse or rotate tokens for the public Workers. See [account API tokens](https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/). These permissions can affect other Workers and databases in the same account if the token is compromised; the workflow's name and binding checks prevent mistakes, not misuse of a stolen token.

## 2. Prepare the protected GitHub environment

1. In [repository settings](https://github.com/enaz333/zane-websites/settings/environments), open **Settings → Environments → New environment**. Enter `cloudflare-studio-production` and select **Configure environment**. Do this before dispatching the workflow.
2. Under **Deployment protection rules**, turn on **Required reviewers** and add only your GitHub account. Leave **Prevent self-review** unchecked if you are the only person dispatching and approving releases. Turn off **Allow administrators to bypass configured protection rules**. Under **Deployment branches and tags**, select **Selected branches and tags → Add deployment branch or tag rule → Branch**, add only `main` and add no tag rule. Save. Confirm `main` is still protected and requires the normal PR checks. If the required reviewer rule is unavailable, stop; do not add credentials or dispatch. See [GitHub deployment environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
3. Under **Environment secrets**, select **Add secret** for each item below. Store them in this environment only, never under repository secrets or variables.

   | Secret | Value |
   | --- | --- |
   | `CLOUDFLARE_ACCOUNT_ID` | Existing Cloudflare account ID |
   | `STUDIO_CLOUDFLARE_API_TOKEN` | New Studio token |
   | `STUDIO_D1_DATABASE_ID` | UUID of the dedicated `zane-studio` database |
   | `ACCESS_TEAM_ORIGIN` | Your HTTPS Access team origin, no trailing slash |
   | `ACCESS_AUD` | AUD tag of the Zane Studio Access app |
   | `STUDIO_OWNER_EMAIL` | Same exact email as the Access Allow rule |

4. Under **Environment variables**, select **Add variable** and set `STUDIO_ORIGIN` to `https://studio.zanegiordano.com` with no trailing slash. Only when ready to request deployment, set environment variable `STUDIO_RELEASE_ENABLED` to `true`. Leave generic production and provisioning settings alone. The deploy step passes the four runtime settings to Cloudflare as Worker secrets; the account token and D1 UUID are not exposed to Studio code or browser assets.

## 3. Approve a Worker deployment with no hostname

1. After merging the validated implementation PR, open **Actions → Release private Studio → Run workflow**. Choose **Branch: main**, **mode: deploy**, and **expected_version: none** for the first release. Leave **rollback_version** blank. For later deployments use the current 100% active Studio Worker version UUID from **Workers & Pages → zane-studio → Deployments**. Do not use a Git commit SHA in this field.
2. Open the queued run. Check the exact main commit and inputs. Select **Review deployments**, choose **cloudflare-studio-production**, and click **Approve and deploy** only for the reviewed run. The workflow checks the reviewed version baseline, verifies the dedicated database, applies migrations, and deploys only `zane-studio`. It cannot attach the hostname. The Actions summary records the commit, previous version, active version and verification outcome. A first run fails if the custom domain is already attached.
3. In Cloudflare, open **Workers & Pages → zane-studio → Settings**. Under **Domains & Routes**, verify that **workers.dev** and **Preview URLs** are disabled and no route or custom domain is attached. Under **Bindings**, verify that **DB** references `zane-studio`. Under **Variables and Secrets**, confirm the four names above are present. Confirm D1 shows the migration in **D1 → zane-studio → Console** using `SELECT name FROM d1_migrations;`. Do not query or export task contents for release verification.

## 4. Separately approve hostname attachment and verify from a phone

1. Reopen **Zero Trust → Access controls → Applications → Zane Studio**. Verify the exact hostname and path coverage, one email Allow rule, and no bypass. Confirm **zanegiordano.com → DNS → Records** has no exact Studio record or applicable wildcard. Check **Workers Routes** and redirect rules for conflicts. Stop for review if anything already owns or redirects the hostname; do not replace records or routes.
2. Only after separately approving hostname attachment, open **Workers & Pages → zane-studio → Settings → Domains & Routes → Add → Custom Domain**. Enter exactly `studio.zanegiordano.com` and select **Add Custom Domain**. Do not enable custom-domain previews or add any other domain. Cloudflare provisions DNS and TLS as part of the attachment. See [Workers custom domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
3. Wait for TLS. In a signed-out browser or with `curl -sS -o /dev/null -D -` (no redirect following), check `/`, `/index.html`, `/studio.js`, `/studio.css`, `/api/projects`, and `/api/tasks`. Expect the Access sign-in challenge on the configured team origin and no Studio content. Don't paste redirect headers or tokens into a public issue. From a private browser session with a different identity, verify denial. On your phone, sign in as the owner and confirm the app and Activity load. With approval for a synthetic smoke submission, create one test request, reload to verify persistence, then cancel it. Confirm `zanegiordano.com/admin` is still inactive. Record results with the Actions run and version ID.
4. After attachment, future releases check anonymous challenges before and after deployment. A valid anonymous redirect does not prove owner access or the identity policy; repeat the phone smoke test after rollout.

## Rollback and first-release recovery

- If a release fails, stop additional runs. Look at the Actions summary and **zane-studio → Deployments**; a failure after upload can leave the new version active. If access behavior is wrong or uncertain, disable/remove **only the Studio Custom Domain** in **Domains & Routes** with owner approval; leave Access in place. Do not enable workers.dev or previews to diagnose the failure.
- For an existing installation, use **Actions → Release private Studio → Run workflow → main → rollback**. Enter the current active UUID under **expected_version** and the previously verified Studio version UUID under **rollback_version**. Review and approve that run separately. It verifies that the target version belongs to this Worker, has the same D1 binding and the required runtime secrets, and confirms the requested version is active at 100%. Use a prior version whose Access configuration still matches the Access app; if you changed the app, prefer a reviewed forward fix. The workflow does not auto-rollback or restore Access rules, domains, DNS or data.
- For a first release there is no prior Worker version. Leave the hostname unattached (or withdraw it if already attached), preserve D1, and fix forward. For later schema changes, review backwards compatibility before deploying: Worker rollback does not undo D1 migrations. Use [D1 recovery](https://developers.cloudflare.com/d1/reference/time-travel/) only through a separately approved recovery plan. See [Cloudflare version rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).

## Verification for this change

Repository validation, fixture-signed JWT tests, local D1 integration and simulated release/rollback tests passed. Wrangler applied the existing migration to disposable local D1 using the generated release config and built the Studio bundle without credentials. The production Worker entry point returned 403 for all six tested HTML, asset and API paths in local Wrangler. The Cloudflare API checks, actual environment approval, remote migration, owner sign-in and DNS/TLS still need the approved rollout.
